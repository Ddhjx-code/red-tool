## v2 期间修掉的致命 bug（全是自造，且靠验证才暴露）

| bug | 机制 | 教训 |
|---|---|---|
| **file:// 完全玩不了** | 加 bloom 时用 `getImageData`；file:// 下 canvas 被位图污染后该调用必抛异常；异常落在 `render()` 内，而 `requestAnimationFrame` 注册在帧末 → **主循环当场死掉、画面定格** | smoke 全程走 **http**，**结构性测不出这条**——测试环境必须覆盖交付环境 |
| **游戏不可通关** | 加沟壑后敌人仍按房间比例撒点 → 一只疫气落在沟里（y≈-997）→ 它卡在坑底打不到 → 房间永清不掉 → **门永不开** | 新增地形时必须同时校验**生成物落点合法性** |
| **验收无效** | 自动机器人不会跳沟 → 卡在第二室 → 那张「Boss 房截图」**根本不是 Boss 房** | 自动化验证路径必须与**真人可玩路径**一致 |
| 主循环抗异常（已加防线） | 任何单帧异常不再杀死 rAF，并通过 `__wh.faulted()` 可观测 | **一个异常不该能打死整个游戏** |

## 视觉门抓到的 6 个真缺陷（全部已修）

这一关的价值不在"通过"，在**它把肉眼短期调不出来的问题变成了数字**。

### ① 链几何折叠：包围盒塌成 62×28px

| 根因 A | `build()` 初始角给 **π**（反了）→ 身体朝 +x 伸到龙头**前方**，应为 `0`（拖在头后） |
| 根因 B | `forward()` 用**位置推导的 `base`** 作参考 → 「翻转→base 翻转→再翻转」正反馈，每节转 ~180° |
| 修法 | `abs.push(0)`；`want = abs[i-1] + wave`（改用**父节角度**，即设计文档所写的「每节一个本地角度」） |

### ② 波数 K 混叠 —— 同时暴露我调研期验证不充分

`K=0.55` → 每节相位差 **198°**，是**混叠锯齿**，不是平滑蛇形。已改 `K=0.14`（每节 50°）。

**我当时用「沿身转角符号翻转 > 4」当判据，而混叠锯齿同样满足它。** 那次数值验证只证明了链长守恒，**没证明「像龙」**。

> 教训：**判据选错时，验证通过反而制造虚假信心。**

### ③ 量纲不自洽

`L=2.0 × 32 节 × SCALE=26 = 1664px`（390px 屏的 4 倍宽）；`FIRE.RISE=26 单位/秒 = 676px/s`。已整套重标定（`L=0.9`、`SCALE=8`、`RISE=4.2` 等）。

### ④ 摄像机朝向错

`AHEAD=0.28` 把头放在**屏幕左侧 28%**，而身体朝左拖 → 大部分身体在屏外。横版卷轴应头在右。已改 `AHEAD=0.66`（头在 257px，尾在 27px，前瞻 133px）。

### ⑤ `render()` 用了陈旧的 camX —— 龙身被画在偏移 ~170px 处（**最关键的一个**）

```js
var m = window.WHScene.metrics();   // 快照：此时 camX 还是上一帧的值
var head = C.head();
window.WHScene.camera(head.x);      // 这里才更新 camX
...
ctx.translate(-m.camX, 0);          // 用的是陈旧的 m.camX
```

后果：**龙身被画到屏幕左边缘外**（那团「纯白 255」就是龙本身），而我沿预期路径采样到的是**那个位置的天空（42）**。我因此得出「龙太暗」的错误结论，还据此**对着一处不存在的病做了整套提亮**（加 `lighter`、加大粒子半径与辉光倍率），结果把龙推成一条均匀饱和到 255 的**无结构白管子**——随后又全部收回。

### ⑥ 过度提亮的回撤

承接 ⑤：提亮后框内过曝达 100%、CV=0（白砖），已收回描边 `lighter`、降低发光贴图峰值 alpha（1.0→0.45）、稀疏化粒子（`EMIT_PER_SEG` 2→1、`POOL` 320→180、半径 0.70/0.30→0.42/0.18）直到 `框内过曝 9% / CV ≈ 1.0`。

---

### ⑦ 画成了「发光管子」，而不是皮影剪影形体（**由用户提问「这是技能特效吗」发现**）

原来的 `drawDragon` 是：32 节点折线 + **三层等宽描边** + 一个 12px 的三角头 + 两根 2.4px 的须。结果就是「一条会扭的均匀发光曲线 + 粒子尘」——**正是 MOBA 里技能光效的视觉语法**。

**我验了延展度、波形、亮度、过曝分布、是否唯一主角，唯独没验「像不像龙」。** 验收标准①写的是「像一条会扭的活龙」，而我没有为它造任何指标。

**根因是视觉语汇用错了**：皮影的正解是「**不透明的影人 + 背光**」——形体由暗剪影给出。我却把龙画成「整体发光」，于是既没有形体，也没有皮影的身份。

**修法（反过来做）**：

| 步 | 做法 |
|---|---|
| 1 | **先立暗剪影形体**：`fillStyle = HUE.near`，沿身构建左右偏移的闭合带，宽度 **1.5 → 0.42 世界单位单调渐变** |
| 2 | **背脊锯齿**：每 2 节一个三角剪影（高度带正弦扰动） |
| 3 | **尾鳍**：末节一个分叉剪影（±1.6 单位） |
| 4 | **头**：楔形剪影（前伸 3.5、宽 ±2.0）+ **两只角**（±3.1） |
| 5 | **节律环**：每 3 节一道暗色横切（影窗语汇） |
| 6 | **再点香火**：沿身一条细暖白亮线（宽 0.5×形体）+ 粒子 |

**修后实测**：头 37–81px / 尾 5–11px → **头尾比 3.9–8.6**（可辨的形体渐变）；背脊锯齿在每 2 节处表现为局部增厚；尾鳍在末节表现为增厚。已固化为断言「头尾粗细渐变成立（头/尾 >= 2.0）」。

**教训**：**「发光」不等于「有形体」。** 主题是「火」很容易让人一路往「更亮」调，而识别性来自**剪影轮廓**。

## 门禁自身的度量错误（3 处，也已修）——**方法论教训最重要**

| # | 问题 | 修法 |
|---|---|---|
| 1 | banding 判据 `Math.round(lum/4)` 把上限卡死在 64 层，却断言 `> 180` —— 自相矛盾 | 改用**未分桶原始亮度**，并补上真正的判别指标：纯天空区**行中位数相邻跳变** |
| 2 | banding 采样竖直列会穿过建筑硬边与星点，那不是 banding | 改**行中位数**（星点稀疏不影响中位数）且只在**纯天空区**（顶部 30%）测 |
| 3 | **沿龙身中心线测 CV 测不出「疏密层次」** —— 中心线永远命中那条窄亮描边（恒 233）→ CV 恒为 0 | 改在**包围盒内**测（亮核心 + 暗间隙 + 稀疏浮尘才有方差） |

### 最重要的一条教训

**我用同一个公式验证了自己。** 采样用的是 `metrics()` 返回的**正确** camX，而渲染用的是**陈旧** camX——所以所有断言都「通过」，而实际画面里龙根本不在那个位置。**度量测的是「我对渲染的模型」，不是「真实渲染产物」。**

正确做法：断言必须建立在**实际像素**上，并且要有一条**交叉校验**——例如「过曝像素是否落在断言所依据的位置」——才能发现「模型与渲染不一致」这类 bug。事后补上的 `过曝 100% 落在龙身框内` 就是这个交叉校验，它才是真正抓住 ⑤ 的那条指标。

## 与原计划的偏离（记录在案）

1. **`WHFire.draw(ctx)` 而非 `draw(ctx, cam)`** —— 世界变换由渲染方持有（否则 `lighter` 合成的 save/restore 与场景分层打架）。
2. **Task 2 就引入最小 `main.js` 承载 `window.__wh`** —— 原计划把 `__wh` 放在 Task 13，但 Task 2 的断言依赖它，照原计划根本跑不了测试。
3. **新增计划外断言** —— 龙身横向铺开 / 不沉入街面 / 纵向摆幅受控。加它们的原因正是「我看不到图」，需要客观代理指标来替代人眼。
4. **`?test=1` 下 rAF 默认暂停** —— 否则动画循环与测试的 `settle()` 交错，不变量断言失去确定性；截图改为「`settle()` → `render()`」完全可复现。
