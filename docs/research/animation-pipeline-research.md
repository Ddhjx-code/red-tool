# 动作游戏动画管线调研

- 日期：2026-09-15
- 触发：下一个工具「2D 横版闯关 / 对决」的可行性。本文只回答一个问题：**角色怎么动起来，以及三条路线的真实成本。**
- 与 [touch-action-research.md](./touch-action-research.md) §4.3 的关系：那份文档把「动画管线」列为第二大阻塞项，本文是对它的收口。**动画管线与屏幕方向正交**——无论竖屏横屏，角色都要动，所以本文不依赖方向实测结果。
- **已定案（2026-09-15）**：题材定为 **中秋·舞火龙**（国家级非遗 Ⅹ-5），形态为横版推进 + 关底 1v1 Boss。本文 §0 第 4 条与 §5 第 4 条以「皮影戏」举例的**推荐结论不变**（走路线 A 程序化骨骼/剪影），但**题材名以定案为准**。舞火龙比皮影更贴合：龙身 **32 节**与骨骼链是**字面意义**的 1:1 映射，且无需人形 IK / 蒙皮 / 朝向层序翻转。见 [wuhuolong-design.md](../specs/2026-09-15-wuhuolong-design.md)。
- 可信度：`VERIFIED` = 有可查来源；`INFERENCE` = 我的推断

---

## 0. 结论摘要

1. **程序化骨骼动画在纯 JS + Canvas 2D 下完全可行，且数学量很小。** 完整的 FK / IK / 关键帧 / 蒙皮公式都有公开推导，核心就是一条 `M_world = M_parent × M_local` 加透视矩阵。**这是零帧资产路线**（`VERIFIED`）。
2. **靠图像模型逐帧生成 sprite 是已知的失败路线。** 实测帧间一致率只有 **60–70%**，头发颜色、护甲比例、装备细节会漂移；「每个角色都对、连起来不是同一个角色」。2026 年的可行做法已经变成**图像出参考帧 → 视频模型驱动动作 → 抽帧打包**（`VERIFIED`）。
3. **真正的工作量在管线而不在生成。** 业界原话：「图像生成约占 20% 工作量，其余 80% 是管线」——抠图、切帧、对齐、一致性校验。这部分需要专门的算法（投影剖面 + DP 最优切割、alpha 加权质心）才能做到不出抖动（`VERIFIED`）。
4. **对本项目，程序化路线（A）是唯一同时满足「包体门禁 + 可扩展性 + 视觉可控」的选项**，且它和「皮影戏」题材是技术同源而非妥协（`INFERENCE`，见 §5）。

## 1. 三条路线对比（按本项目的实际约束核算）

约束前提（1.6.0）：zip ≤10 MiB、建议 ≤2 MiB、单条 Base64 ≤1 MiB、无构建链、ES2017、Canvas 2D、无 WASM/Worker。

| | **A. 程序化骨骼 / 剪影** | **B. 2.5D 纸片木偶** | **C. 逐帧 sprite（AI 生成）** |
|---|---|---|---|
| 资产需求 | **零帧资产**（纯矢量或少量分件） | 每角色 8–15 个分件 | 每动作 6–12 帧 × 多动作 × 多角色 |
| 包体 | 极小（代码 + 少量图） | 中（分件 WebP） | 1 角色 6 动作 ×8 帧 ≈ 288 KB（扁平风）；**扁平 ≤3 角色可压进 2 MiB** |
| 加一个新招式 | **改关键帧数据 ≈ 零资产成本** | 改关键帧，可能需补分件 | **重出 8 帧 + 跑一遍管线** |
| 翻转朝向 | 免费（`scaleX = -1`） | 免费 | 免费（镜像） |
| 换色 / 变体 | 免费（改填充色） | 较易 | 需重出 |
| 视觉上限 | 抽象 / 剪影 | 中高（保留插画质） | **最高** |
| 代码量 | 骨骼+FK+IK+关键帧 ≈ 400–800 行 | 同 A + 分件对齐 | 运行时只要序列帧播放（很小），**但需一整套构建期资产管线** |
| 主要风险 | 视觉上限不够，被嫌「廉价」 | 关节接缝穿帮 | **管线工程量 + 美术一致性；且新增内容边际成本最高** |

**关键判断**：C 的包体不是死路（扁平风小阵容能过门禁），但它**新增一个招式的边际成本是「重跑一遍资产管线」**，而 A 是「改几个数」。对一个需要多招式、多敌人、要反复调手感的动作游戏，这个差异是决定性的。

## 2. 路线 A：程序化骨骼动画（技术可行性）

### 2.1 数学骨架（全部有公开推导，可直接照写）

2D 齐次变换（3×3 矩阵，含平移/旋转/缩放），骨骼绕自身关节旋转必须用**枢轴**形式：

```
M_pivot = T(p) · R(θ) · T(-p)
```

世界矩阵逐级相乘：

```
M_world(child) = M_world(parent) · M_local(child)
v_world        = M_world(child) · v_local
```

更新顺序（从根遍历一次）：

```
updateWorld(bone, parentWorld):
    local = translate(position) · translate(pivot) · rotate(angle)
            · scale(scale) · translate(-pivot)
    bone.world = parentWorld · local
    for child in bone.children: updateWorld(child, bone.world)
```

反向运动学：双骨用**余弦定理解析解**；n 骨链用 **FABRIK**（Forward And Backward Reaching IK）。

关键帧插值：`x(t) = x0 + (x1 - x0) · f(u)`，`u = (t - t0)/(t1 - t0)`；缓动函数只需满足 `f(0)=0, f(1)=1`。

### 2.2 六个必踩的坑（这些是路线 A 的全部风险所在，逐条有来源）

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 枢轴不在分件局部坐标 | 肢体绕画布左上角公转 | 用 `T(p)·R·T(-p)`，`p` 存局部坐标 |
| 2 | 直接套子骨 `M_local` | 子骨不跟父骨动 | 必须 `M_parent · M_child` |
| 3 | 矩阵逐帧累乘 | 角度缓慢漂移、缩放跑偏 | **只在标量通道上存状态，每帧从通道重建矩阵**；绝不 `matrix = matrix · Δ` |
| 4 | **两个姿势做矩阵逐元素插值** | 过渡中角色「缩一下」再恢复。2D 单轴解析解：**`det = (1 + cosθ)/2`**——差 **45°** 取中点掉到 **0.854**（缩 ~15%），差 **90°** 掉到 **0.50**（**缩 50%**），差 180° 直接 **0**（塌成一条线） | 分解回 TRS 通道分别插值：位置线性、缩放线性、**角度走最短弧**，再重组 |
| 5 | 角度直接数值插值 | 350° → 10° 反向转 340° | `delta = ((target - start + 180) % 360) - 180` |
| 6 | 绘制顺序跟着骨骼树 | 转身后手臂穿帮 | **绘制顺序与骨骼层级解耦**；每个分件存两个层序值，按朝向选一个 |

补充：位置类通道用**单调保持**的三次插值（Fritsch–Carlson：局部极值处切线置零），否则脚落地那一下会过冲；但**关节角度应当保留过冲**——那正是「回弹感」的来源，一律加单调约束会把整套动画的弹性抽干。

### 2.3 次级运动（头发 / 衣摆 / 灯穗）——纯代码

二阶弹簧 + 比例增益即可，无需物理引擎：

```
dest += (initial - dest) * springGain;
cur  += (dest - cur)  * propGain;
```

同一个模式还能低成本做「呼吸」「行走起伏」：以 `sin` 驱动根骨位移、以 `cos` 驱动腿部旋转，相位错开即得步态。

### 2.4 现成参考实现（学技法，不 vendor）

| 项目 | 可学什么 |
|---|---|
| `urraka/skel2d` | 骨骼层级 + slot/attachment + 时间轴数据格式（受 Spine 启发） |
| `1j01/skele2d` | 以「点 + 骨段」为世界建模单位的引擎 + 姿势/动画混合 |
| `EsotericSoftware/spine-runtimes`（canvas 示例） | Canvas 2D 骨骼渲染全流程（**商业授权，只读不抄**） |
| haotianblog 2D 动画系列 | FK / 双骨 IK / 蒙皮 / 关键帧四篇的公式推导与不变量测试表 |
| Godot 官方 cutout 教程 | 分件层级、髋为根、`RemoteTransform2D` 解耦层序、IK 链 |

值得注意：haotianblog 那篇给了一张**矩阵代码的单元测试表**（单位姿势、仅根平移、仅父旋转、枢轴自映射、骨长保持）——这正是本项目「用无头断言替代肉眼验收」的既有习惯可以直接套用。

## 3. 路线 C：AI 逐帧（2026 真实管线与失败模式）

### 3.1 失败模式（多种独立来源一致）

| 问题 | 表现 |
|---|---|
| **mixels**（假像素画） | 放大后不成网格 |
| **frame bleeding** | 朴素网格切割把角色切碎 |
| **frame drift** | 播放时滑动、上下跳、抖 |

图像模型**逐帧单独生成必然漂移**。原话：「一个英雄被渲染八次『行走第 3 帧』，披风长度、武器尺寸、护甲细节仍会漂移——模型不知道自己一秒前画了什么。」

量化：通用 AI 图 **60–70%** 帧间一致率；专用系统号称 94%。

### 3.2 正在工作的管线（三段式）

```
参考帧（图像模型，锁角色身份）
  → 动作驱动（图像→视频：Kling 3.0 Omni / Wan 3.0 / Seedance 2.5）
  → 抽帧 + 抠图 + 切帧 + 对齐 + 打包
```

- **为什么必须走视频**：视频模型有**时间先验**，20 帧内能保持剪影一致；图像模型逐帧没有。
- 现实成功率：**行走循环首跑约 70% 可用**，其余要删/重生 2–3 帧。
- 帧数经验值：行走 6–8 帧，待机 4–6，攻击 5–8。

### 3.3 真正耗工程的 80%（这些算法是硬要求）

| 环节 | 朴素做法（会坏） | 正确做法 | 实测改善 |
|---|---|---|---|
| 抠图 | 固定 RGB 阈值 chroma key | **YCbCr 色度空间** + 洪泛填充 + 形态学 | 品红残留 2739 → 2 px |
| 切帧 | 等分 / 连通域 | **垂直 alpha 投影剖面 + DP 全局最优切割** | 切到角色的切线 8/8 → **0/8** |
| 对齐 | 包围盒中心 | **alpha 加权质心**（重心） | 质心抖动 σ 27.2 → **0.2 px** |
| 身份校验 | 人眼 | 64-bin RGB 直方图 + dHash 感知哈希（两轴） | — |
| 抽帧 | seeked 事件 | **`requestVideoFrameCallback`**（seeked 在 P 帧多的片上会重复取帧） | — |

**绝对不能做**：每帧独立裁剪/重新居中。那会制造假的镜头运动。必须用 `preserve-canvas`——所有帧共用同一画布尺寸与粘贴位置。

### 3.4 对「非遗/国风」系列的具体风险

`docs/series-plan.md` 记录：打铁花 **v1–v6 六版视觉未达标，产品代码已删除**。视觉密集 + 无资产管线是本项目**已被证实的失败模式**。路线 C 恰恰是「视觉密集 + 需要新建一整套资产管线」的组合——它的视觉上限最高，但也最贴近那条已经死过一次的路。

## 4. 路线 B：2.5D 纸片木偶

介于 A 与 C 之间：每个角色拆 8–15 个分件（插画质），用 A 的骨骼系统驱动。

- 好处：保留插画质感，动画仍是程序化（可加招式、可翻转、可换色）
- 代价：分件拆分与枢轴标定要人工；**关节接缝**是主要穿帮点（需要重叠余量 + 描边 + alpha 合成；有来源提到「看到白缝不要只补描边，要查共享边界、重叠余量、权重归一化」）
- 包体：分件 WebP，单角色约 150–400 KB（比 C 省，因为不需要每动作每帧）

**这是最可能的「升级路径」**：先 A 把玩法与手感跑通，若视觉评审判定剪影不够，再把角色换成 B 的分件——**骨骼系统与关键帧数据可以整体复用**，不需要重写动画层。这是 A→B 相对 A→C 的结构性优势。

## 5. 推荐：先做单角色 vertical slice，用 A 路线验穿

**建议顺序：A（验玩法与手感）→ 判定视觉上限 → 需要则升级到 B → 仍不够才考虑 C。**

理由：

1. **A 是唯一「加招成本≈0」的路线**，而动作游戏必须反复调手感、加招式、加敌人。这一个理由就压过视觉上限的差距。
2. **打击感与动画质量解耦**。前面的调研已确认：打击感来自**受击方的反应**（鬼泣制作人原话），而 hitstop / 震屏 / 命中火花全是代码。A 路线对「受击方怎么反应」有完全控制权 → **单位资产的打击感产出最高**。
3. **A→B 的迁移是结构性的**：骨骼系统、关键帧格式、绘制管线全部复用，只换分件资源。所以选 A 不锁死视觉上限。
4. **题材上是技术同源，不是妥协**。皮影戏本身就是**关节木偶 + 背光剪影**（`docs/research/datiehua-research.md` 已核实：联合国非遗编号 00421，影人 12–24 个活动关节，传统上就是表现武打的媒介）。剪影不吃材质与细节精度——**这正好绕开打铁花卡死的那道坎**。用程序化骨骼驱动皮影，是「用对的工具做对的题材」。
5. **风险可控**：A 的全部坑已在 §2.2 列出并各有正解，且能写单元测试（用无头断言替代肉眼验收，符合本项目既有习惯）。

**vertical slice 的最小验收面（建议）**：
- 1 个角色 × 1 套三段连招（起手/命中/收招）× 1 个敌人 × 1 段横版地形
- 触屏载荷机制：一键连招 + 自动朝向 + 输入缓冲 + 判定窗放宽
- 打击感四件套：hitstop + 震屏 + 命中火花 + **受击方夸张反应**
- 动画层：FK 骨骼 + 双骨 IK + 弹簧次级运动 + 朝向翻转层序
- 无头断言：矩阵不变量（§2.2 那张表）+ 帧间骨长保持 + 连招状态机可达性

跑通后再量真实成本，决定是否放大阵容、是否升级到 B。
