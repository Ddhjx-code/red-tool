# 移动端触屏横版动作玩法调研

- 日期：2026-09-15
- 触发：下一个工具候选「2D 横版闯关 / 对决小游戏」（参照 ICEY、4399 死神vs火影），用户指定参照 DNF 手游的触屏解法
- 前提纠正：本项目**真实使用场景是纯触屏、App 内**，没有键盘、没有鼠标、没有 PC 场景（PC 模拟器仅用于开发预览）。本文所有结论按这个前提展开。
- **已定案（2026-09-15）**：题材定为 **中秋·舞火龙**（国家级非遗 Ⅹ-5），形态为横版推进 + 关底 1v1 Boss。本文 §5 第 5 条推荐的「剪影 / 关节链」路线成立，但**题材名以定案为准**（舞火龙而非皮影戏）；它同样是剪影 + 关节链，且龙身 32 节与骨骼链是 1:1 映射。见 [wuhuolong-design.md](../specs/2026-09-15-wuhuolong-design.md)。
- 可信度标记：`VERIFIED` = 有可查来源；`INFERENCE` = 我的推断，无直接来源；`UNVERIFIED` = 来源可疑或无法交叉验证

---

## 0. 结论摘要

1. **触屏横版动作有成熟解法，但解法不是「把键盘搬到触屏」。** 行业做法是**放弃搓招**，改用「一键连招 + 智能施法 + 自动索敌」。DNF 手游开发者日志完整记录了这个试错过程（`VERIFIED`）。
2. **竖屏动作游戏已被商业验证**，但验证的是「单指/低精度」形态（拖动移动、松手出拳），不是 ICEY 式硬核 ACT（`VERIFIED`，见 §1.4）。
3. **容器屏幕方向是未决的阻塞项。** 没有任何公开文档说明小红书小工具是否支持横屏；所有间接证据指向竖屏（`VERIFIED` 无文档 + `INFERENCE` 结论）。
4. **真正的成本是动画管线，不是玩法代码。** 打击感可以 100% 程序化，但角色动作序列需要一套当前项目没有的管线（见 §4.3）。

## 1. 触屏动作的行业解法

### 1.1 DNF 手游：搓招为什么必须放弃（`VERIFIED`）

来源：DNF 手游开发者日志第一期「战斗操作篇」，4399 转载 2019-06-12
<https://m.4399.cn/news-id-890535.html>

开发者原文记录的试错路径：

| 阶段 | 尝试 | 结果 |
|---|---|---|
| 1 | 端游式搓招（组合键/方向指令） | **放弃** |
| 2 | 两套按键自由切换 | **放弃** |
| 3 | 一键连击键 | 采用 |

放弃搓招的两条原因（原文）：

> 「虚拟摇杆跟端游键盘的操作体验差异大，导致手游中搓招成功率很低。」
> 「虚拟摇杆有一定的延时性，导致很多技能在手游搓招时，会造成多余的位移。」

同样原文：「端游每个职业约有 30 多个技能，可通过快捷键和组合键（搓招）来释放；手游只能摆放 10 个左右的按键图标。」

最终采用的四件套：

| 机制 | 做法 | 对玩法的意义 |
|---|---|---|
| **一键连击键** | 连续点击同一按键，按预设顺序施放多个技能；共 4 套连招，每套最多 5 个技能，起手技能不可重复 | 用「点击节奏」替代「指令输入」，把连招从操作技巧变成配置 |
| **CD 自动跳过** | 连招套路中某技能在 CD 时自动跳过，释放下一个 | 保证连招不因 CD 中断（稳定性优先于精确性） |
| **技能滑屏键** | 1 个按键配 4 个技能，上下左右滑屏施放 | 在有限按键数下扩容 |
| **技能轮盘** | 方向性技能用轮盘施放，「便捷性和视觉引导方面效果更佳」 | 解决方向技能的瞄准引导 |
| **智能施法** | 子弹自动追踪；量子爆弹/烈焰冲击等自动瞄准最近敌人 | 原文：「手游操作不如端游精准」，故添加智能施法降低难度 |

另有可调项（来自操作设置攻略，`VERIFIED`，游民星空 <https://www.gamersky.com/handbook/202405/1747282.shtml>）：
- **摇杆类型**：固定型 / 移动型 / 悬浮型（悬浮型手指离开也不归位）
- **摇杆方向**：8 方向（新手）或 32 方向（精细）
- **敏感度、位置、尺寸**可调
- **疾闪发动方式**：建议「后跳拖拽」而非「双击后跳」——因为拖拽单键就能调方向，双击还要同时控摇杆
- 可关闭「普攻拖拽」让操作更流畅

> 对本地化的意义：**「一键连招 + 自动索敌 + 可调摇杆」不是简化，是触屏动作的必要载荷。** 缺了任何一个，玩法在触屏上都不成立。

### 1.2 街霸：对决（`VERIFIED`）

来源：Cocos 官方稿 <https://www.cocos.com/post/c6224c1be072bf5556817749c32e40c6>

- 「将原有的搓招技能进行调整，既能享受连招的快感，又可以**一键释放大招**」，加入即时 QTE 连击
- 「制定了一套**碰撞框检测系统**，可以非常精确地显示目标的受击位置，产生爆点」
- 「针对每一个打击点，都配置相应的**命中顿帧和震屏**效果」
- 动作帧处理：**「弱化过渡、突出打击帧和命中帧」**，角色模型头身比定为 4.5
- 结论原话：「简化了技能释放难度，极大降低了上手门槛……但游戏依然保留着格斗游戏最重要的微操设计」

### 1.3 鬼泣-巅峰之战：打击感的真相（`VERIFIED`）

来源：GameRes 制作人分享 <https://www.gameres.com/874754.html>

三个对本项目直接有用的结论：

1. **打击感的来源是「对方的反应」，不是特效。** 原文：
   > 「打击感最重要的一点实际上是跟怪物的配合，因为你的打击感的反馈来自于对方……打对方一拳，如果对方不动，不光不动，还没有任何变化，你就会觉得你在做一个无效动作……一定是你在打到他的时候，他做了一个很夸张的反应。」
   
   震屏、钝帧、特效都只是辅助。

2. **AI 行为树组：主动限制同时攻击数。** 原文：
   > 「当玩家周围出现两只以上怪物时，其他怪物的攻击欲望就会降低，这能有效避免战斗场面的混乱。」
   
   这是动作游戏不被围殴致乱的关键机制，且是纯逻辑。

3. **动作融合**：受击状态可直接接新动作，不必先回待机态——「使角色的打击和受击感受更加的真实」。

另：关卡由策划先搭白模（blockout）验证，再交美术加工。

### 1.4 竖屏动作的先例（部分 `VERIFIED`）

**《唯我独尊》/ I, The One（CASUAL AZUR GAMES）** — `VERIFIED`（3 个独立来源互相印证）
来源：<https://www.tyg888.com/wangyou/20349.html>、<https://pmm.pcpop.com/detail/36508.html>、<http://m.jxdown.com/app/127433.html>

- **同时提供竖屏与横屏两套操作**：
  - 横屏：左侧虚拟摇杆移动 + 右侧攻击/技能按钮
  - **竖屏：单指拖动移动，松手即自动出拳**
- 竖屏单指被玩家评价为「一只手就能玩，走路排队都能玩」
- 连招通过不同攻击顺序触发回旋踢/上勾拳/抱摔；单局 1–3 分钟
- 目标是把对手击出擂台（物理击飞），不是血条对拼

**《霓虹武馆》/《刃心·序章》竖屏动作数据** — `UNVERIFIED`
来源为一篇低质量聚合站文章（xusyun.com），文中「《崩坏：星穹铁道》竖屏副本测试版次留 43.7%」「腾讯光子《刃心·序章》」「B站《霓虹武馆》DAU 85 万」等数据**无法交叉验证，标题可能虚构，不要引用**。

但该文中三条竖屏动作设计经验在原理上自洽，暂记为 `INFERENCE`：
- 竖屏把横向视野压成纵向聚焦：敌人自上而下压进屏幕，闪避路径压缩为上下滑动/左右倾斜
- UI 信息重排：《霓虹武馆》把血条、能量槽、连击数**沿右侧边缘垂直排列**；关键提示用**微震动 + 色块脉冲**代替文字弹窗
- 三条「铁律」：单局 90–150 秒；核心战斗循环压缩到「发现→逼近→爆发→收招」四步；成长系统卡片式垂直堆叠、避免横向翻页

### 1.5 归纳：触屏动作的载荷性设计

| 机制 | 缺了会怎样 | 本项目可实现性 |
|---|---|---|
| 一键连招（连点接招 + CD 自动跳过） | 玩家打不出连段，动作游戏退化成单招对拼 | ✅ 纯逻辑 |
| 自动索敌 / 自动朝向 | 触屏瞄不准，命中率崩 | ✅ 纯逻辑 |
| 判定窗放宽（相对 60fps 帧数） | 触屏误差让判定不可信 | ✅ 纯逻辑 |
| 输入缓冲（动画中按键仍生效） | 操作「丢招」，手感发涩 | ✅ 纯逻辑 |
| 打击感演出（hitstop / 震屏 / 火花 / **受击方夸张反应**） | 打上去「无效动作」感 | ✅ 纯代码，零资产 |
| 多怪攻击欲望调度 | 被围殴致乱、无法读招 | ✅ 纯逻辑 |
| 虚拟摇杆 | 无法移动 | ✅ **已有现成实现**，见 §3 |
| 微震动触感反馈 | 反馈通道减少（非致命） | ⚠️ 容器未明确允许，见 §4.2 |

**结论：触屏动作玩法在纯 JS + Canvas 2D 下完全成立，且载荷性机制全部是纯逻辑或纯程序化演出，不需要美术资产。**

## 2. 容器约束核对（`VERIFIED`，来自 .skill 1.6.0）

| 约束（1.6.0 规范） | 对横版动作的影响 |
|---|---|
| 纯本地、不联网 | **不能联机 PvP**；「对决」只能是 vs AI（本地同屏双人在单机手机上不成立） |
| 禁 Web Worker / SharedWorker / ServiceWorker | 物理、AI、渲染逻辑全在**主线程** |
| 禁 WebAssembly | 不能用 Box2D/PhysX 的 WASM 构建；物理需纯 JS |
| 无构建链（本仓库现状：无 package.json/vite） | 手写 ES2017；禁 `?.`、`??`、对象展开、逻辑赋值、`BigInt` 字面量；无 `type="module"`，靠 `window` 命名空间 |
| 包体 ≤10MiB（建议 ≤2MiB）；单条 Base64 ≤1MiB | 帧动画若走 Base64 内嵌会很快撞墙 |
| 文件类型白名单：图片/字体/json | **无 mp3/wav/ogg**；`data:`/`blob:` 媒体亦被禁 → 音频只能 Web Audio 程序化合成（12 个工具已解决） |
| WebGL 有 GPU 分档与降级要求；**Canvas 2D 不受该分档约束** | **2D 动作应走 Canvas 2D**，避开 DPR/纹理/draw call 预算与 context lost 义务 |
| 容器外壳统一控制导航栏/下拉刷新 | 全屏靠 CSS 沉浸式布局，不能 `requestFullscreen` |
| 挂载组件只在 App 内渲染，Web 端不可玩 | 无头测试靠 Playwright（项目已有 15 套 smoke） |

> 摇杆实现里已写死了两条血泪教训（原文注释）：
> - `setPointerCapture` 是 best-effort，对 inactive pointer 会抛 `NotFoundError`，部分手机根本不兑现 → **必须 try/catch，失败不能中断拖拽**
> - pointermove 要绑在 `window` 而不是摇杆容器上 → 手指滑出 72×72 底盘后容器上不再收到事件、摇杆会静默失效；用 `pointerId` 门控保证全屏拖动且一定释放

## 4. 未决的阻塞项

### 4.1 容器屏幕方向 — 最高优先级（`UNVERIFIED`）
**没有找到任何公开文档说明小红书小工具的屏幕方向行为。** 间接证据全部指向竖屏：

- 小红书自身的规范体系是竖屏优先（官方推荐 3:4 竖版，「单列信息流、用户手持手机上下滑动」）
- 组件挂载在笔记下方、在 App 信息流内渲染（本项目已有调研结论）
- 官方小程序「多端适配指南」只讨论平板/折叠屏的**宽度**缩放（`Width ≤ 480dp 等比缩放`），从不讨论旋转：<https://miniapp.xiaohongshu.com/doc/DC263909>
- 本仓库 18 个工具全部按 **390×844 竖屏**构建与测试；无一个做方向锁定（`tools/bobing/assets/scene.js:1755` 只有 `orientationchange → onResize`，跟着转、不锁）

**建议的验证顺序**（任一条即可定性）：
1. 向平台/官方 FAQ 确认是否支持横屏
2. 上传一个最小横屏测试小工具，实测渲染行为
3. 保守路径：直接按竖屏设计，把方向问题从风险变成前提

> 这一项决定整个形态：横屏才算真「横版」；竖屏则要么改成「竖屏 letterbox 横条带」，要么改成「竖版推进动作」。

### 4.2 触感反馈 `navigator.vibrate`（`UNVERIFIED`）
不在 1.6.0 的禁用清单里，但也不在允许清单里。触屏动作中微震动是低成本高收益的反馈通道（§1.4 的竖屏 UI 方案用到），需确认。

### 4.3 动画管线 — 最大的真实成本（`VERIFIED` 为项目历史事实）
项目现有素材管线是 `wan2.7-image-pro` + `rembg` → **静态 WebP**（hanfu 81 组、shanzi 6 棋子）。动作游戏需要**动作序列**：起手 / 命中 / 收招 / 受击 / 倒地 × N 帧 × N 个角色。AI 出图给不了帧序列，必须走以下之一：

| 路线 | 成本 | 画风代价 |
|---|---|---|
| 程序化矢量 / 骨骼动画 | 低（零帧资产） | 必须接受抽象/剪影风 |
| 2.5D 纸片木偶绑定（分件 + 变换） | 中（需分件资产） | 可保留插画质 |
| 逐帧手绘 或 AI 补帧 | 高 | 上限最高、周期最长 |

**必须正视的前车之鉴**：`docs/series-plan.md` 记录打铁花 `v1–v6 六版视觉未达标，2026-08-13 删除产品代码`。视觉密集 + 无资产管线是本项目**已知的失败模式**，而动作游戏的价值恰恰高度依赖视觉手感。

> **已收口**：本条已在 [animation-pipeline-research.md](./animation-pipeline-research.md) 展开为三条路线的成本对比与推荐。结论是**先走程序化骨骼/剪影（零帧资产）做单角色 vertical slice**，因为它是唯一「加一个招式≈零边际资产成本」的路线，且 A→B（分件木偶）的迁移可复用整个动画层。本文其余部分不依赖该结论。

### 4.4 平台时机（`VERIFIED`）
国风 vibecoding 大赛 **9/14 已截止**（今天 9/15）。下一个工具按「自然流量 + 系列沉淀」定位，不再有赛道时间压力 → 可以用更长的验证周期做形态验证。

## 5. 对落地的启示

1. **别把「横版动作」当作必须重资产的项目。** 玩法层（状态机 + hitbox + 一一连招 + 自动索敌 + 输入缓冲 + 打击感演出 + 多怪调度）可以在无资产前提下做完，且这正是触屏动作的载荷部分。
2. **打击感优先做「受击方反应」**（§1.3），而不是堆特效。这是投入产出比最高的一环，且纯代码。
3. **先解决 4.1（方向）再谈形态。** 如果容器竖屏锁定，ICEY 式的横向视野压迫感与多目标处理逻辑（§1.4 提到的横屏优势）就不成立，必须重设战斗空间。
4. **动画管线要作为独立决策提前定**，不要等玩法做完才发现角色动不起来。可行的组合是先做**单角色 vertical slice**（1 个角色 × 1 套连招 × 1 个敌人 × 1 段横版地形），把「动画路线 + 手感 + 触屏载荷机制」一次性验穿，再决定是否放大。
5. **形态上走「剪影 / 皮影」路线**：它同时绕开 4.1 的视野依赖和 4.3 的帧资产依赖（关节木偶天然程序化动画、剪影不吃细节精度），且题材在 `docs/research/datiehua-research.md` 已核实过（皮影戏，联合国非遗编号 00421，传统上就是表现武打的媒介）。**该路线已在 [animation-pipeline-research.md](./animation-pipeline-research.md) §5 完成论证并给出推荐顺序（A 程序化 → 判定视觉上限 → 需要则升级 B 分件木偶 → 仍不够才考虑 C 逐帧）。**
