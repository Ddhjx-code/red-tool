# 存储结构与发布前自检

小工具是单页应用，但「什么算状态、什么算临时变量、字段怎么加、发布前查什么」
这几件事会被`ohmygame`的规则卡得很准。它做的是多屏叙事游戏，我们只要它的两条。

## 1. 界面拥有表现和输入，状态拥有流程

原文一句话：**Nodes own presentation and input. The Runtime owns state and flow.**

拆成我们能用的：

| 归属 | 该放什么 | 不该放什么 |
| --- | --- | --- |
| 界面（DOM / 视图函数） | 当前展开的弹层、输入中的值、滚动位置、动画中间态 | 用户数据本身 |
| 状态（`store.js` 的数据对象） | 跨视图要留的东西、要落盘的东西、要进备份的东西 | 可以被重算出来的派生值 |

判断标准很直接：**离开这个视图再回来，它还需要在吗？** 需要就在状态里，
不需要就是视图的事。月历的 `sheetCtx`（当前弹层在编辑哪一天）就是视图的事，
`episodes`（记了哪几次）才是状态。

## 2. 状态只能改已有的键

原文（`docs/playable-nodes/runtime.md:243-253`）：

> `initialState` 的顶层键是唯一的键。`set` 和 `patch` 不能新建顶层键；要用新键，
> 必须先加初始值。

为什么这么定：新建键意味着「有人在运行时偷偷造了数据结构」，
迁移、备份、校验都无法预期它的存在。

对我们的意思：

- `episodes`、`settings` 这些键的初始值写在一个地方（默认配置），别分散
- 加 `symptoms` 这类新键时，**先在默认配置里给它 `[]`**，再写读写它的代码
- 版本迁移是把旧数据补成新形状，不是让读取代码去猜「没有就当空」

月历现在的 `store.js` 就是「读的时候兜底」的思路：能用，但字段一多会散。
下次改存储时按这条收紧。

## 3. 校验分两档

`docs/playable-nodes/agent.md:211-222` 定义了两种校验：

| 档位 | 查什么 | 相当于我们的 |
| --- | --- | --- |
| `draft` | 语法、引用、每个视图的源文件和它 import 的东西 | `tests/spec_compliance_scan.py` 现在做的事 |
| `publish` | draft 全部 + **每个 signal 都有去处、每个源文件都存在** | 还没做 |

`publish` 档多出来的部分，正好是「点了没反应」这类问题：

1. 页面里每个可点的元素，都有对应的事件处理（没有处理的不该长得像按钮）
2. 每个 `<script src>` / `<link href>` / 图片路径都真实存在
3. 每个存储键在初始配置里都有默认值
4. 每个视图都能到达，也都能离开（没有只进不出的死路）

这四条是它给的，不是我们自己编的，可以直接照着加。

## 4. 验证方式：走一遍，不是扫一遍

原文对「改完之后怎么算完」的定义：

> 打开 → 重置 → 走到改动的地方 → 执行真实交互 → 在状态里确认 signal 和目标 → 截图

我们的等价动作：

```sh
# 1 静态门禁
python3 tests/spec_compliance_scan.py

# 2 真实交互（无头 Chrome + 模拟存储，参考 promo/yueli/src/make-preview.py）
./promo/yueli/src/shoot.sh        # 四张界面截图，肉眼过一遍

# 3 关键路径：首次录入 → 记一笔 → 改 → 删 → 刷新后仍在
```

**截图这一步不能省。** 静态扫描通过、控制台无报错、但界面错位的情况太多，
尤其是改过 CSS 之后。

## 5. 一条容易被忽略的规则

原文：`返回栈只存 ID，不存实例`（`runtime.md:275`）；跨界面要活下来的东西必须在 State 里。

对应到我们：视图切换时，不要留着一个 DOM 引用当状态——重新渲染时那个节点已经没了。
只留「我现在在哪个视图、要展示哪天的数据」这种可序列化的东西。
